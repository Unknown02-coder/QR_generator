# QR 저장·목록·미리보기 백엔드 설계

## 목적과 범위

로그인한 사용자가 브라우저에서 만든 QR을 명시적으로 저장하고 `내 QR`에서 자신의 목록과 썸네일을 확인한다. 비로그인 입력·미리보기는 기존 프론트엔드가 계속 처리한다. PNG·SVG 다운로드와 삭제는 다음 기능으로 남긴다.

## API 계약

- `POST /api/qrs`: 세션·CSRF 필수. `{type,title,payload}`를 받아 201과 `{id,type,title,summary,createdAt}` 반환. `type`은 `url`, `wifi`, `contact`, `text`, `email` 중 하나다. 제목은 trim 후 1~80자, 페이로드는 비어 있지 않아야 하며 실제 QR로 인코딩 가능해야 한다. 유형과 페이로드 형식이 모순되면 400이다.
- `GET /api/qrs?page=1&size=5&type=url`: 세션 필수. `type`은 선택값. `{items,total,page,pageSize}`를 반환한다. 최신 저장순, 같은 시각이면 ID 역순으로 정렬한다. 페이지는 1부터 시작하고 5건 고정이다. 범위를 넘는 페이지는 빈 `items`와 실제 `total`을 반환한다.
- `GET /api/qrs/{id}/preview`: 세션 필수. 소유자의 저장된 페이로드에서 256×256 PNG를 다시 생성한다. 없는 ID와 타인 ID는 모두 404다. `Cache-Control: no-store`를 설정한다.
- 비로그인 API 호출은 기존 JSON 401, CSRF 누락은 JSON 403을 유지한다. 잘못된 입력은 JSON 400이다.

## 저장과 보호

Flyway `V2`가 `saved_qrs` 테이블을 만든다. 각 행은 UUID ID, `users.id` 소유자 FK, 유형, 제목, 암호화 페이로드, 생성 시각을 가진다. 조회는 항상 소유자 조건을 포함한다. 목록 응답과 로그에는 원문 페이로드를 포함하지 않는다. `summary`는 유형별 고정 문구로 만들며 Wi-Fi 비밀번호와 연락처 상세를 포함하지 않는다.

페이로드는 서버 환경 변수 `QR_ENCRYPTION_KEY`의 Base64 인코딩 32바이트 키로 AES-256-GCM 암호화한다. 매 저장마다 새로운 12바이트 nonce를 만들고, 버전 바이트·nonce·암호문을 함께 저장한다. 소유자 ID와 QR ID를 추가 인증 데이터로 묶어 다른 행으로 옮긴 암호문도 복호화되지 않게 한다. 키가 없거나 길이가 잘못되면 서버 시작을 실패시킨다. 테스트 프로필의 키는 공개된 테스트 전용 값만 사용한다.

## 생성과 검증

서버는 ZXing으로 QR 용량을 검증하고 미리보기 PNG를 만든다. UTF-8, 오류 정정 M, 검정 모듈·흰 배경, 4모듈 여백을 사용한다. 실제 저장될 문자열을 그대로 인코딩한다. 클라이언트의 미리보기 성공만 신뢰하지 않는다.

## 확인 기준

1. 다섯 유형의 유효한 페이로드를 저장하고 자기 목록에서 최신순·유형 필터·5건 페이지네이션으로 조회한다.
2. DB의 암호문과 목록 응답에 원문, Wi-Fi 비밀번호, 연락처 상세가 없다.
3. 다른 계정은 해당 항목을 목록·미리보기로 볼 수 없고, 비로그인 저장·목록은 401이다.
4. CSRF 누락 저장은 403, 잘못된 유형·제목·페이로드는 400이다.
5. 미리보기 PNG를 다시 읽으면 저장한 페이로드와 정확히 일치한다.
6. H2 기반 테스트를 통과한다. Docker가 있는 환경에서는 PostgreSQL 마이그레이션·저장 테스트도 실행한다.

## 결정 근거

이번 브랜치에서 썸네일 API까지 구현하는 이유는 프론트엔드 `내 QR` 목록이 저장 항목마다 이미지를 요청하기 때문이다. 다운로드·삭제는 독립적인 사용자 동작이라 별도 브랜치에서 검증한다. 저장 시 미리보기와 같은 원문을 보내고, 서버는 그 원문이 실제 QR로 인코딩되는지 다시 확인한다.
