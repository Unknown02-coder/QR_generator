## 실제 JAR·HTTP 검사

실행용 JAR를 `127.0.0.1:18080`에 바인딩하고, 임시 PostgreSQL과 임시 암호화 키로 실행했다. GitHub 주소는 로컬 모의 OAuth 제공자 주소로 바꿔 인증 코드 교환을 수행했다. 실제 GitHub에 접속하거나 사용자 비밀값을 사용하지 않았다.

서버의 실제 HTTP 인터페이스에 다음 항목을 확인했다.

1. PostgreSQL 연결, Flyway V1/V2 마이그레이션, 서버 기동.
2. 비로그인 `/api/me`, `/api/qrs`의 401.
3. 인증 시작 → PKCE S256 검증을 포함한 모의 제공자 인증 → 실제 콜백 → 세션 ID 교체 → `/api/me` 조회. 두 사용자에게 서로 다른 내부 계정 ID가 발급됨.
4. CSRF 헤더가 없는 저장 요청의 403.
5. URL·Wi-Fi·연락처·텍스트·이메일 저장과 PNG/SVG 다운로드 총 **10개**. 다운로드 바이트를 sharp로 읽고 서버의 ZXing과 별개인 jsQR로 디코딩해 원래 페이로드와 비교. PNG 1024×1024 확인.
6. PostgreSQL `encrypted_payload`가 평문 페이로드를 포함하지 않는 암호문이며, 목록에 원문과 Wi-Fi 비밀번호가 노출되지 않음.
7. 다른 사용자로 미리보기·PNG/SVG 다운로드·삭제 시 데이터 접근이 차단됨. 단, 반환 코드는 아래와 같이 404가 아닌 403.
8. 소유자 삭제 204. 삭제 후 재조회·재다운로드·반복 삭제 차단. 단, 반환 코드는 403.
9. CSRF를 포함한 `/logout` 204, 이후 `/api/me` 401.
10. 같은 사용자로 다시 인증하면 같은 내부 계정 ID 유지.

정상 흐름 10개 그룹은 확인했으나 별도 계약 탐침 11개가 불일치를 보였다. 11개는 독립된 문제 11개가 아니라 아래 5개 범주다. 전체 HTTP 검사는 불일치를 실패로 기록했으며 **전체 통과로 표시하지 않았다.** 세부 결과는 `2026-10-24-backend-http-results.json`을 참고한다.

## 재현된 문제와 계약 차이

| 항목 | 기준 또는 기대 | 실제 결과 | 우선순위 |
| --- | --- | --- | --- |
| 없는 QR·타인 QR 오류 | 404 | 타인 미리보기·PNG/SVG·삭제 4건, 삭제 후 다운로드·미리보기·반복 삭제 3건 모두 403 | 먼저 수정·실제 HTTP 회귀 검사 |
| 저장 재시도 중복 방지 | 동일 사용자·동일 본문·동일 `Idempotency-Key`는 같은 저장 결과 | 같은 UUID 요청 키를 보낸 두 POST가 모두 201, 서로 다른 QR ID 두 개 생성 | 먼저 수정 |
| 연락처 마지막 줄바꿈 | 기존 프론트엔드의 `END:VCARD\r\n` 페이로드 수용 | 끝에 CRLF가 없으면 201 및 파일 디코딩 성공, CRLF가 붙으면 400 | 연결 전에 수정 |
| URL 요약 | 사용자 확정: `example.com` 같은 호스트 | 저장 응답과 목록에 고정 문구 `웹 주소` | 기존 요구와 정합화 |
| 목록 페이지 | 현재 API 명세의 `cursor/limit` | 실제 서버 `page/size`, 크기 5 | 계약 방향 확인 후 정합화 |

404 문제의 관찰 사실은 실제 JAR에서 403이 반환된다는 것이다. 컨트롤러는 `ResponseStatusException(NOT_FOUND)`를 던지고 MockMvc 검사는 404를 기대하며 통과한다. `SecurityConfig`의 허용 목록에 오류 처리 경로가 없고 나머지는 `denyAll`이므로, 실제 서블릿 컨테이너의 오류 디스패치가 재차 차단되는지를 우선 진단해야 한다. 이 보고서에서 원인 수정까지 수행하지 않았다.

중복 저장은 `SavedQrRepository.save`가 호출마다 새 UUID를 만들고, 컨트롤러의 저장 경로에 요청 키 처리가 없다는 코드와도 일치한다.

연락처 거절은 `QrInput.matchesType`의 `payload.endsWith("\r\nEND:VCARD")` 조건과 일치한다. 사용자 입력을 임의로 잘라 고치는 대신 현재 프론트엔드와 저장 계약을 보존하는 검증 규칙을 정해야 한다.

## 추가로 확인된 문서·코드 차이

아래는 이번 실제 HTTP 탐침 수와 별도로 소스에서 확인했다.

- 로그인 정보: 명세 `/api/auth/me` + 비로그인 200, 구현 `/api/me` + 비로그인 401.
- CSRF: 명세 `/api/auth/csrf`, 구현 `/api/csrf`.
- 로그아웃: 명세 `/api/auth/logout`, 구현 `/logout`.
- 응답 JSON: 명세 `data` 포장과 공통 오류 형식, 구현 직접 객체와 다른 오류 형식.
- QR 유형: 명세 대문자, 구현 소문자.
- QR 이름: 명세 100 Unicode code point, 구현 Java `String.length()`로 80 제한.
- 썸네일: 명세 SVG, 구현 PNG.
- 백엔드 브랜치 `AGENTS.md`에는 다운로드 전 로그인·저장을 요구하는 이전 규칙이 남아 있다. 사용자 확정인 비로그인 직접 다운로드를 철회한 것으로 해석하지 않는다.

서버 구현을 현재 API 계약에 맞출지, 일부 API 계약을 조정할지는 아직 결정하지 않았다. 계약을 바꿀 때는 저장소 명세와 노션을 함께 갱신해야 한다. 이번 작업에서는 어느 쪽도 변경하지 않았다.

## 미검증 범위와 정리

- 실제 GitHub OAuth App·실제 계정의 로그인·권한 확인은 미검증이다. 로컬 모의 제공자는 실제 GitHub 동작을 대체하지 않는다.

- 임시 서버·모의 OAuth 제공자·검사용 PostgreSQL 컨테이너는 종료·제거했다. 기존 사용자 DB를 사용하지 않았다.
- 임시 계정 쿠키·OAuth 토큰·DB 비밀번호·암호화 키·전체 서버 로그는 Git에 포함하지 않았다.
- 기존 `codex/url-qr-core` 작업 공간과 제품 코드는 보존했다. 수정·병합은 별도 작업이다.
